# ぶらり旅機能 仕様書

本書では、donguri における「ぶらり旅」企画のための動画管理・再生機能の仕様を定める。

## 1. 概要

ぶらり旅とは、通常配信とは別に事前編集された動画を再生する企画である。
転換シーン中に、通常転換 / CM に加えて、事前に用意された動画（複数）から 1 本を選んで再生できる。

本機能では以下を行う。

- Controller（`/`）: 動画のアップロード・削除・選択・再生・停止を操作する
- Viewer（`/viewer`）: OBS ブラウザソース上で、Controller から指示された動画を全画面再生する

## 2. 前提・運用形態

| 項目             | 内容                                                                                   |
| ---------------- | -------------------------------------------------------------------------------------- |
| Controller       | 通常のブラウザ（Chrome 等）で `http://<host>:5173/` を開く                             |
| Viewer           | **OBS のブラウザソース**で `http://<host>:5173/viewer` を開く                          |
| 起動方法         | `npm run dev`（開発）/ `npm run build` → `npm run preview`（本番運用）                 |
| 楽曲データ       | 従来どおり `GET /performances` で取得。**変更しない**                                  |
| 動画フォーマット | **mp4 のみ**対応                                                                       |
| 動画保存先       | リポジトリ直下の `videos/` ディレクトリ（`.gitignore` 対象、ブラウザリロード後も残る） |

### 2.1 通信アーキテクチャ

Viewer は OBS ブラウザソース（Controller を開くブラウザとは別プロセス）で動くため、Controller のブラウザとは **BroadcastChannel / IndexedDB / localStorage を一切共有できない**。
そのため、純粋なフロントエンドだけでの通信は不可能であり、**Vite の開発サーバーを中継役（リレー）とする**。

- 本リポジトリ内の Vite プラグイン（`server/donguriServerPlugin.ts`）としてサーバーミドルウェアを実装する
- `configureServer`（dev）と `configurePreviewServer`（preview）の両方に同じミドルウェアを組み込み、`npm run dev` と `npm run preview` の双方で動作する
- Controller ↔ Viewer のリアルタイム通信は、Vite サーバー上の **WebSocket リレー `/burari/ws`** で行う
- リレーは受信した JSON イベントを、送信元を含む全接続クライアントへブロードキャストする
- 既存の送出系イベント（`/performance/start`、`/performance/music`、`/conversion/start`、`/conversion/cm-mode`、`/display-copyright`、`/force_mute`）も、本リレー経由で送信する
- OBS が Vite サーバーへ HTTP / WebSocket で到達できれば、同一マシンでも別マシンでも動作する

### 2.2 動画の保存方式

- Controller 上のアップロードボタンから Vite サーバーのアップロードエンドポイントへ送信し、サーバーが `videos/` に保存する
- `public/` 配下に置かないため、hot reload によって配信状態が崩れる問題を回避する
- ファイルはディスク上にあるため、ブラウザをリロードしても消えない
- エクスプローラーで `videos/` に直接 mp4 を置いても認識される（一覧はサーバーがフォルダを読むため）

## 3. 機能仕様

### 3.1 Controller 側 UI

配置場所: 転換操作エリア（`ConversionMenu`）の下部に、ぶらり旅セクション（`ConversionBuraritabi` コンポーネント群）を配置する。

#### 3.1.1 動画ソース選択

- `videos/` 内の mp4 ファイルをファイル名順に一覧表示し、その中から **1 つを選択**できる
- 選択 UI はドロップダウン形式とする
- 各動画には**削除ボタン**を配置する（選択中の動画も削除可能）
- 動画ごとに、最終配信時刻と累計配信回数を表示する
- **アップロードボタン**: `accept="video/mp4"` のファイル入力を開き、**複数ファイルを同時にアップロード**できる
  - アップロード中は「アップロード中...」と表示する
  - アップロード完了後、自動的に一覧を更新する
  - 同名ファイルが存在する場合は 409 エラーとなり、エラーメッセージを表示する
  - `.mp4` 以外のファイル、パストラバーサルとみなされるファイル名はサーバー側で拒否される

#### 3.1.2 プレビュー

- 選択中の動画を Controller 上でプレビューできる
- プレビューは**ミュート**で再生する
- 再生 / 一時停止ボタン、シークバー、現在時間 / 総時間の表示を持つ
- 表示 / 非表示を切り替えられる（非表示中は動画リソースの読み込みを止める）

#### 3.1.3 再生・停止

- **再生ボタン**: 選択中の動画の再生を Viewer に指示する（`/burari/play` 送信）
- **停止ボタン**: 再生中の動画を停止し、Viewer に停止を指示する（`/burari/stop` 送信）
- 再生開始後、Controller は「ぶらり旅再生中」状態となり、画面上部にバッジを表示する
- 再生中は「再生中: {filename}」と停止ボタンを表示する
- Viewer から再生終了イベント（`/burari/ended`）を受信したら、自動的に再生中状態を解除する
- **保険**: Controller 側でも動画のメタデータから duration を取得し、`duration + マージン（数秒）` のタイマーを持つ。終了イベントが届かなくてもタイマー満了で `/burari/stop` を送信し、操作不能に陥らないようにする

#### 3.1.4 操作可能条件

| 操作             | 可能条件                                                                                   |
| ---------------- | ------------------------------------------------------------------------------------------ |
| 動画選択         | 常に可能                                                                                   |
| 動画アップロード | 常に可能                                                                                   |
| 動画削除         | 転換シーン中 かつ ぶらり旅再生中でないこと                                                 |
| 再生             | 転換シーン中 かつ 選択中の転換が現在のトラックであること かつ CM OFF かつ 再生中でないこと |
| 停止             | ぶらり旅再生中であること                                                                   |

- CM 再生中（CM トグル ON）は、ぶらり旅の再生ボタンを disabled とし、「CM中なので再生不可」と表示する
- 転換が選択されていない（現在のトラックでない）場合は、「転換が選択されていないため再生不可」と表示する
- ミュート ON のときは、画面上部のステータスバーに「ミュート中」を表示する（ぶらり旅の操作自体は可能）

#### 3.1.5 エラー表示

- 動画一覧取得失敗、アップロード失敗、削除失敗時に、赤文字でエラーメッセージを表示する
- エラーメッセージは手動で閉じることができる

### 3.2 Viewer 側

- `/burari/play` を受信したら、指定された動画を**画面全体を覆う `<video>` オーバーレイ**で自動再生する（音声あり）
- `/burari/stop` を受信、または動画の `ended` イベント発火時に、オーバーレイを外して元の転換シーンに戻す
- 動画の `ended` 時は、WebSocket リレー経由で Controller に `/burari/ended` を送信する
- ぶらり旅再生中に他のイベント（送出、CM 切替等）が届いても、動画再生を中断しない
- ミュートはぶらり旅と同期しない。Viewer は音声を常に出力し、実際のミュートは下流（ミキサー / OBS）で掛かる前提

### 3.3 サーバー API

| メソッド / パス                   | 内容                                                                          |
| --------------------------------- | ----------------------------------------------------------------------------- |
| `GET /burari/videos`              | `videos/` フォルダ内の mp4 一覧を返す（`[{ filename, size }]`）               |
| `POST /burari/videos`             | mp4 をアップロードして `videos/` に保存。`.mp4` 以外は 400、同名は 409 で拒否 |
| `DELETE /burari/videos/:filename` | 該当ファイルを削除                                                            |
| `GET /burari/videos/:filename`    | 動画本体を配信。**Range リクエスト対応**                                      |
| `WebSocket /burari/ws`            | イベントリレー。受信した JSON イベントを全接続クライアントへブロードキャスト  |

- ファイル名はパストラバーサル対策としてサニタイズする（`..`、`/`、先頭 `.` 等を拒否）
- WebSocket のパスは Vite 自身のホットリロード用 WebSocket と衝突しないよう専用パスとし、`httpServer` の `upgrade` イベントでパスを見て振り分ける

### 3.4 WebSocket リレーのイベント仕様

既存イベント:

- `/performance/start`、`/performance/music`、`/conversion/start`、`/conversion/cm-mode`、`/display-copyright`、`/force_mute`

新規イベント:

| type            | 方向                    | data                   |
| --------------- | ----------------------- | ---------------------- |
| `/burari/play`  | Controller → Viewer     | `{ filename: string }` |
| `/burari/stop`  | Controller → Viewer     | `{}`                   |
| `/burari/ended` | Viewer → Controller     | `{ filename: string }` |
| `/relay/hello`  | サーバー → クライアント | `{ epoch: string }`    |

- リレーサーバーはイベントに `offset` を採番し、メモリ上に直近のイベントログを保持する
- クライアントは接続時に `lastOffset` と `epoch` を渡し、未受信分の再送を受ける（Viewer の OBS 内リロード・再接続時に転換シーン状態を復元するため）
- サーバー再起動時は `epoch` が変わるため、クライアントは古い `lastOffset` を破棄して全イベントを受信し直す

## 4. 制限事項・非対応

- mp4 以外の動画フォーマット対応
- 動画のリネーム・差し替え（同名ファイルは拒否される。差し替えたい場合は削除後に再アップロード）
- Viewer 側でのミュート状態の自動反映
- アップロード容量制限の厳密な管理（ディスク容量に依存）
